Concurrent is not the same as parallel

Does concurrent mean parallel? Short version: no, the two words answer different questions. Hover or tap any dotted word to see what it means and where the word comes from.

ConcurrentSeveral tasks are in progress during the same period. Their steps may interleave. It is about how the work is structured: Rob Pike’s phrase is “dealing with” many things at once.
ParallelSeveral tasks are executing at the same instant, on different cores. It is about execution: Pike’s phrase is “doing” many things at once.

⇄ marks a context switch. In the middle mode, the work finishes no sooner than sequentially, and in a real machine each switch also costs a little time, so it can finish later. Concurrency gives structure and responsiveness, not speed. Speed needs the second core. Pike mentions people being surprised when a program got slower on 4 processors.

The “4 processors” paradox. The remark Pike quotes (“I ran the prime sieve with 4 processors and it got slower!”) illustrates the confusion his talk addresses: his slides call the reaction “Concurrency is cool! Yay parallelism!!” a fallacy. The prime sieve is the example program in the Go language specification: a chain of pipeline stages, each a goroutine that copies numbers from its input to its output while removing the multiples of one prime. The Go FAQ explains that whether a program runs faster with more CPUs depends on the problem: intrinsically sequential problems cannot be sped up by adding CPUs, and sometimes more CPUs slow a program down, because passing data between threads involves context switches that have a significant cost, which can grow with more CPUs. The FAQ names this sieve as an example: it has no significant parallelism although it launches many goroutines.

OSTEP’s multiprocessor chapter describes two costs that come with more CPUs. One is cache coherence: CPUs that keep copies of the same memory in their caches must be kept consistent. The other is synchronization: access to shared data structures needs locks, and the chapter notes that as the number of CPUs grows, access to a synchronized shared structure becomes quite slow. The same chapter observes that a typical application uses a single CPU, so adding CPUs does not make that single application faster.

Amdahl’s law, as stated in Gustafson’s 1988 paper, puts a number on the limit set by serial work. If s is the fraction of the work that must run serially, the speedup on N processors is 1 ÷ (s + (1 − s) ÷ N), so the maximum with unlimited processors is 1 ÷ s. With s = 10% and 4 processors that is about 3.1 times, and never more than 10 times. Gustafson adds that the formula assumes a fixed problem size; when the problem grows with the number of processors, much higher speedups are possible.

The common thread in these sources: whether extra processors help depends on how much of the problem can truly be done independently, and on what the coordination costs.

Real life: browser, editor and terminal at once

Picture a browser, a code editor and a terminal open together. Each is made of one or more processes, and each process of one or more threads. Most of the time every one of those threads is idle: the browser waits for the network, the editor waits for the next keystroke, the terminal waits for a command. OSTEP distinguishes three process states (running, ready, blocked): a blocked thread is waiting for an event, is not ready to run, and needs no core. Only ready threads compete for cores, and the scheduler decides which of them runs.

This is what each machine does with them. Choose a machine:

What happensShort bursts of work, mostly gaps. The core is handed to whoever has work ready, and switched away the moment that work is done or its slice runs out.

Switching this fast is what makes the apps look simultaneous. On the example desktop PC described below (4.38 GHz), a core completes about 4.4 billion clock cycles per second, so a 10 ms slice (a value used in OSTEP’s examples) is roughly 44 million cycles. Nielsen Norman Group puts the limit for a system to feel as if it reacts instantly at about 0.1 second, so switching much faster than that looks simultaneous.

5,574 threads share 32 logical processors, about 174 threads for each, yet only 4% of the CPU’s capacity was being used, which is about 1.3 logical processors’ worth of work (4% of 32). So nearly all of those threads were waiting. This is concurrency in its everyday form: thousands of things in progress, a handful actually executing at any instant. (The 32 come from SMT: each of the 16 cores presents two logical processors, and AMD lists the 5950X as 16 cores and 32 threads.)

The drawing is simplified: real apps use far more than three threads. A real scheduler also tends to keep a thread on the same core, because the data it was using is still close by, but it may move the thread to balance the load (OSTEP covers this in its multiprocessor scheduling chapter).

What a core is

A core is one CPU. OSTEP describes a multicore processor as a chip with multiple CPU cores packed onto it. The chip is the processor; AMD lists the Ryzen 9 5950X (the example PC below) as 16 cores and 32 threads, which is why spec sheets quote both numbers.

Without SMT, a core executes one thread at a time. With SMT, a core handles two threads simultaneously: Intel explains that the two threads share the core’s execution resources while some components, such as register files, are duplicated, and the operating system sees each thread as a logical processor. Because the resources are shared, the two logical processors of one core are not equivalent to two separate cores. A 4-core chip without SMT can run 4 threads at the same instant; with SMT, up to 8.

Who decides what runs where

A desktop PC can have hundreds of processes and far fewer cores. The operating system’s scheduler hands out the cores in short time slices. This is time sharing, the technique the OSTEP textbook uses to explain how an OS virtualizes the CPU: each program gets the illusion of having its own. To move a core from program X to program Y, the OS saves X’s registers and program counter (its context) and loads Y’s. That is a context switch. The OS can also take the core back by force, which is preemption.

So on one core there is concurrency without parallelism: fast switching looks simultaneous but is not. On several cores there are both.

Process vs thread

POSIX defines a process as an address space with one or more threads executing within it, plus the system resources those threads need. A thread is a single flow of control within a process, and many of the process’s resources are shared among all its threads. A fork() call creates a new process that is an exact copy of the caller, so parent and child have separate memory, including any text still waiting in an output buffer. Threads of one process share memory, and OSTEP’s concurrency chapters explain that updating shared data without coordination leads to race conditions.

Reading fork() output

  • After fork(), parent and child are two independent processes: that is concurrency.
  • If the scheduler puts them on different cores they also run in parallel; on one core they take turns. A program cannot tell which, and must not depend on it.
  • The order of their printf calls is therefore nondeterministic: it can change from run to run. That is how output such as mini$ child here ends up on one line: a shell prompt and a child’s text share one terminal.

The same idea in six languages

Only some languages expose the real fork call. C (through POSIX) and Python on POSIX systems do. Node.js, Java, Go and C# offer something different: a way to start a new program as a child process. In every case two processes end up running concurrently, which is the idea this page is about, but the child does not begin as a copy of the parent. Each tab says which case it is and why. The echo command used by the Java, Go and C# examples is an executable on Linux and macOS. The Go documentation notes that its own examples assume a Unix system and may not run on Windows; on Windows, substitute any real program.

Caveats worth knowing

  • The words are not fully settled. Pike (“Go Concurrency Patterns”, 2012) defines concurrency as the composition of independently executing computations, a way to structure software, and says it is not parallelism although it enables it. The Silberschatz, Galvin and Gagne textbook Operating System Concepts (chapter 4) says concurrency supports more than one task making progress, while parallelism means a system can perform more than one task simultaneously. The wording differs, but both agree that a single processor can be concurrent without being parallel; Pike states it directly.
  • More cores do not mean proportionally more speed. The Go FAQ says it depends on the problem; see the “4 processors” paradox above.
  • Everyday English can mislead. Oxford Learner’s Dictionaries defines concurrent as happening at the same time, so the everyday word already suggests simultaneity, whereas in computing it is used for tasks in progress over the same period even if they do not execute at the same instant.
