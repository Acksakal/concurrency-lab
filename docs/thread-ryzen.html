Ryzen Thread Lab

Real threads on real cores. You run the C program on your machine; this page draws what your CPU actually did.

What we're testing

The previous page drew threads one step at a time. Your Ryzen 9 5950X has 16 cores and 32 hardware threads, so here several steps really happen at the same instant. Three questions:

  1. Where and when do threads actually run? Do they run in parallel? What changes on a single CPU?
  2. Does the race from level 2 really happen? Does a mutex really fix it? Is one CPU enough to cause it?
  3. Is "one step at a time" always a valid picture? We'll catch a result that no step-by-step order can produce.

Step 1 · Build and run on Cygwin

Save the source, then in the Cygwin terminal, in the same folder:

gcc -std=gnu90 -O2 -Wall -Wextra -pedantic -pthread ryzen_lab.c -o lab
./lab > out.txt

It takes roughly 10 s to a minute and should compile with no warnings. -O2 matters: the racy code uses volatile so the compiler keeps every load and store we wrote. Optional arguments: ./lab RACE_N SB_ITERATIONS (defaults 2000000 and 1000000).

Experiment 2 · The race from level 2, for real

Two threads each run count++ N times, so the expected total is 2N. Without a mutex, count++ compiles to three separate instructions:

movq g_count(%rip), %rax ; load addq $1, %rax ; add (in a private register) movq %rax, g_count(%rip) ; store

Each bar is one run. The black line on the right is the expected total. Hover a bar for the exact numbers.

Experiment 3 · A result that no step-by-step order can produce

Two shared variables start at X = Y = 0. The two threads run at the same time:

thread A: X = 1; r1 = Y;
thread B: Y = 1; r2 = X;

Try it the old way. In every one-step-at-a-time interleaving, one of the two stores happens first, so at least one thread must see a 1. (r1, r2) = (0, 0) looks impossible. The program repeats the test a million times and counts every outcome.

How a real core produces (0, 0): step through it

Each core has a store buffer: a small private queue where its writes wait before they reach shared memory. The core reading its own writes sees them right away. Other cores don't see them until the buffer drains.

The picture to keep

"Observed" means it happened in the data you loaded. A "may" item that didn't show up wasn't proven impossible: it just didn't happen in this run. A "may not" item is guaranteed by POSIX or by the CPU's rules. If you ever observe one, there's a bug.

Sources

  • POSIX.1-2024 · pthread_create(): the new thread's ID need not be stored before the thread starts executing.
  • POSIX.1-2024 · pthread_mutex_lock() and Base Definitions ch. 4 (Memory Synchronization): applications must synchronize access to shared memory.
  • Microsoft Learn · Multiple Processors: on SMP any thread can run on any processor, and affinity restricts that.
  • Intel 64 and IA-32 SDM, Vol. 3, "Memory Ordering": loads may be reordered with older stores to different locations. AMD's APM Vol. 2 states the same rule for AMD64.
  • Jeff Preshing · Memory Reordering Caught in the Act: the classic version of experiment 3, first run on Cygwin.
