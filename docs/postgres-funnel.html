The leader funnel

How a PostgreSQL parallel query runs, and why more workers sometimes help a lot and sometimes not at all.

The setup

An online shop has an orders table. When PostgreSQL runs a parallel query, the work is split among several processes. Both names below are official PostgreSQL terms (hover any dotted word for its meaning and English origin):

  • Workers, officially background worker processes. When the Gather node is reached, the process serving your session requests them. Each one scans part of the table: in a parallel sequential scan, the table's blocks "will be divided into ranges and shared among the cooperating processes".
  • The leader: the process serving your session, which runs the Gather node. It "must also read all of the tuples generated by the workers" (a tuple is a row), and it sends the results on to your client.

Every result row passes through the leader: many workers in, one way out. On this page I call that a funnel, which is my metaphor, not a PostgreSQL term. Pick a query and a number of workers, then press Play.

The default max_parallel_workers_per_gather is 2. Going above 2 requires raising it, and the pool is also capped by max_parallel_workers and max_worker_processes (both 8 by default). If fewer workers are available than planned, the query simply runs with fewer.

Simulation rules (my simplifications, not PostgreSQL internals): time moves in ticks, and each tick a process has 4 units of work. Scanning 1 row costs 1. For the leader, receiving 1 row from a worker costs 1 and passing it on to the client costs 1. Each worker hands its rows over through a small queue of 8 rows; when the queue is full, the worker is blocked. Workers need 12 ticks to start; the leader starts immediately. The last two rules come straight from the docs for parallel_leader_participation: workers can "become blocked because the leader is not reading tuples fast enough", and without leader participation, the leader must "wait for worker processes to start up".

What the PostgreSQL docs say

    

      

        
The two cases

        
"When the parallel portion of the plan generates only a small number of tuples, the leader will often behave very much like an additional worker, speeding up query execution."

        
"…when the parallel portion of the plan generates a large number of tuples, the leader may be almost entirely occupied with reading the tuples generated by the workers…"

        
Section 15.1, How Parallel Query Works. Query 1 is the first case and query 2 is the second.

        
"Setting this value to off reduces the likelihood that workers will become blocked because the leader is not reading tuples fast enough, but requires the leader process to wait for worker processes to start up before the first tuples can be produced."

        
Description of parallel_leader_participation, Resource Consumption chapter. This is the red "blocked" state in the animation.

        
The fix: send less through the funnel

        
For aggregates, PostgreSQL works in two stages. "Each process participating in the parallel portion of the query" (the leader too, if it participates) computes a Partial Aggregate over its own rows. Only those partial results are transferred to the leader, which combines them in a Finalize Aggregate. That's query 3: each worker sends one tuple (its count) instead of every matching row.

        
Section 15.3.3, Parallel Aggregation.

      

      

        
The planner prices the hand-over

        

          
SettingDefaultMeaning (from the docs)

          
cpu_tuple_cost0.01cost of processing each row

          
parallel_tuple_cost0.1cost of transferring one row from a worker to another process

          
parallel_setup_cost1000cost of launching the worker processes

          
parallel_leader_participationonwhether the leader also runs the scan itself

        

        
So the planner assumes that transferring a row from a worker costs 10× as much as processing it (cost units are arbitrary, only the ratios matter). For a query like 2, it will usually judge a parallel plan not worth it and choose a plain Seq Scan. You could encourage parallel plans to see this for yourself, for example with SET parallel_setup_cost = 0; SET parallel_tuple_cost = 0;, but the funnel would still be there.

        
Same lesson as your counter

        
In your C experiment the mutex was the funnel: every increment had to pass through it one at a time, so extra threads only added waiting. The leader is a funnel for rows. Parallelism pays off when workers do a lot of work on their own and send very little through the shared point.
