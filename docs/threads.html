Prerequisite: concurrent vs parallel

POSIX threads in C, from the core idea

A program normally runs one sequence of instructions. POSIX threads (pthreads) let one process run several sequences, each called a thread, all working on the same memory. That sharing is the point and the difficulty at once: cooperation becomes cheap, and mistakes become possible. One idea runs through every section below: shared memory needs rules. Each section pairs a picture or animation with a small C program that was compiled and run.

Dotted words show a meaning and an origin on hover or tap. The difference between concurrent and parallel is covered in the earlier page; only the part needed here is repeated.

How the examples were checked. Every C program on this page is written in C90 with GNU extensions (gnu90): declarations at the top of each block, /* */ comments only, no C99 features. Each was compiled with gcc -std=gnu90 -Wall -Wextra -pedantic -pthread, which produced no warnings (neither did the stricter -Wc90-c99-compat -Wdeclaration-after-statement), and run on Linux (Ubuntu 24.04, GCC 13.3, 2 cores). Printed outputs are copied from those runs and marked as such. Timing-dependent output differs between runs and between machines, so a run on Cygwin will show different numbers, and that is expected. The animations are models that follow the rules described; they are not measurements of hardware.

1. One process, many threads

POSIX describes a thread as a single flow of control within a process. Each thread has its own thread ID, scheduling attributes, errno value and the resources needed for its own flow of control, such as a stack. Everything whose address a thread can obtain, including global variables, storage from malloc() (the heap) and local variables, is accessible to all threads of the same process (POSIX.1-2024, XBD chapter 3, “Thread”).

That is the difference from a new process. After fork(), the child is a copy of the parent, so each has its own variables and a write in one is invisible to the other. A new thread gets no copy: it runs inside the same address space. The picture below shows both. Switch the mode and press the button: the second flow writes x = 99.

Where threads run is a separate layer. The operating system’s scheduler decides which thread runs on which core, and with smt a core presents several logical processors. None of that changes what the picture shows: the threads share memory wherever they run.

2. Creating and joining threads

2.1 The first program

Three threads are started, each prints one line, and the main thread waits for all of them.

hello_threads.c
#include <pthread.h>
#include <stdio.h>
#include <string.h>

static void *worker(void *arg)
{
    int id = *(int *)arg;

    printf("hello from thread %d\n", id);
    return NULL;
}

int main(void)
{
    pthread_t tid[3];
    int ids[3];
    int i, rc;

    for (i = 0; i < 3; i++) {
        ids[i] = i;                       /* one slot per thread */
        rc = pthread_create(&tid[i], NULL, worker, &ids[i]);
        if (rc != 0) {                    /* error NUMBER, not errno */
            fprintf(stderr, "pthread_create: %s\n", strerror(rc));
            return 1;
        }
    }
    for (i = 0; i < 3; i++)
        pthread_join(tid[i], NULL);       /* wait for each thread */
    printf("all threads finished\n");
    return 0;
}
  • pthread_create(&tid, attr, start_routine, arg) starts start_routine(arg) in a new thread. It returns 0 on success; otherwise it returns an error number. The error number is returned, not placed in errno, which is why the program passes rc to strerror.
  • The start routine has the type void *(*)(void *): one pointer in, one pointer out. Returning from it ends the thread.
  • pthread_create returns immediately. The new thread may run at once, later, or on another core; the order is up to the scheduler.
  • join: pthread_join(tid, &result) waits until the thread has terminated and stores the value it returned.
  • -pthread belongs in both the compile and the link step. The GCC manual describes it as the option for POSIX threads support, available on GNU/Linux, most other Unix systems, and x86 Cygwin and MinGW.

Most runs printed 0, 1, 2, but two other orders appeared, while “all threads finished” was always last: the joins guarantee that. Rare is not the same as impossible: a different machine, load or operating system (such as Cygwin) can make other orders common. This is the first rule of thread output: between threads, order is not promised unless something enforces it. The animation steps through one possible timeline for each order seen above.

2.2 Passing arguments: who owns the memory?

The new thread reads arg when it runs, not when pthread_create returns. If arg points at a variable that the creating thread keeps changing, the new thread sees whatever value is there at the moment it looks. The program above avoids this by giving each thread its own slot, ids[i]. The animation contrasts it with the tempting &i.

The same reasoning covers lifetime: a pointer to a local variable of a function that has already returned points at memory that is no longer valid. Data handed to a thread must outlive the thread’s use of it.

3. Data race: two threads, one counter

Two threads each add 1 to the same variable a million times. The expected total is two million.

race.c
#include <pthread.h>
#include <stdio.h>

#define N 1000000L

static long counter = 0;                  /* shared by both threads */

static void *work(void *arg)
{
    long i;

    (void)arg;
    for (i = 0; i < N; i++)
        counter++;                        /* not atomic: load, add, store */
    return NULL;
}

int main(void)
{
    pthread_t a, b;

    pthread_create(&a, NULL, work, NULL);
    pthread_create(&b, NULL, work, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("expected %ld, got %ld\n", 2 * N, counter);
    return 0;
}

The statement counter++ looks like one step, but on typical hardware it is three: read the value into a register, add 1 there, write the register back. Each thread has its own registers; the variable is in shared memory. If both threads read before either writes, one increment is lost. The optimizer is free to keep counter in a register inside the loop, which shrinks the window in which the threads collide, but the program is still wrong: correct output on a given run is luck, not a guarantee.

Race condition and data race

OSTEP calls the situation a race condition: the result depends on the timing of the code’s execution. POSIX gives the memory-level case a precise name. A data race exists when two threads make conflicting accesses to the same memory location (at least one a write), at least one of the accesses is not atomic, and neither access is ordered before the other (POSIX.1-2024, XBD 4.15.1.1). The consequence is not just a wrong number: a program with a data race has undefined behavior, so the language promises nothing about it.

ThreadSanitizer is a compiler-based tool that finds data races while the program runs. On the same program, built with gcc -std=gnu90 -g -O0 -fsanitize=thread -pthread on Linux, it printed (abridged, first of two warnings):

WARNING: ThreadSanitizer: data race (pid=2762)
  Read of size 8 at 0x55fa68080018 by thread T2:
    #0 work race.c:14
  Previous write of size 8 at 0x55fa68080018 by thread T1:
    #0 work race.c:14
  Location is global 'counter' of size 8
  Thread T2 created by main thread at: ... pthread_create ... main race.c:23
  Thread T1 created by main thread at: ... pthread_create ... main race.c:22
SUMMARY: ThreadSanitizer: data race race.c:14 in work

The report names the variable, the two threads, and where each was created. Line 14 is the counter++ statement. That same run printed expected 2000000, got 2000000: the total happened to be right, and ThreadSanitizer still reported the race. A correct result does not mean a correct program.

4. Mutex: taking turns

A mutex is a lock object. Only one thread at a time can hold it; a thread that tries to lock a held mutex is made to wait until the holder unlocks it. Code between lock and unlock is a critical section: only one thread at a time can be inside it, so the three machine-level steps can no longer be interleaved with another thread’s. The model below is the same as before with lock and unlock around the increment. Try the same bad order: the second thread’s attempt to take the lock is refused until the first thread unlocks.

mutex.c
#include <pthread.h>
#include <stdio.h>

#define N 1000000L

static long counter = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

static void *work(void *arg)
{
    long i;

    (void)arg;
    for (i = 0; i < N; i++) {
        pthread_mutex_lock(&lock);        /* enter the critical section */
        counter++;
        pthread_mutex_unlock(&lock);      /* leave it */
    }
    return NULL;
}

int main(void)
{
    pthread_t a, b;

    pthread_create(&a, NULL, work, NULL);
    pthread_create(&b, NULL, work, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("expected %ld, got %ld\n", 2 * N, counter);
    return 0;
}

Rules that go with a mutex

  • Initialize it: PTHREAD_MUTEX_INITIALIZER for a static mutex, as in the program above, or pthread_mutex_init().
  • The thread that locked a mutex is the one that unlocks it. For the default mutex type, unlocking a mutex that the caller does not hold is undefined behavior (POSIX.1-2024, pthread_mutex_lock).
  • Locking a normal mutex that the same thread already holds deadlocks that thread (same page).
  • The lock only helps if every access to the shared variable goes through it. One unlocked access is enough to bring the data race back.
  • Locking is not free: threads that collide on the lock wait, so the work inside it should stay short.

5. Deadlock: everyone waiting, nobody running

A deadlock appears when each thread in a group holds something and waits for something another member holds. OSTEP lists four conditions that must all hold: mutual exclusion, hold-and-wait, no preemption, and circular wait. Two mutexes locked in opposite orders are enough. The animation shows the locks and who holds or wants them. Use the buttons to let each thread take its first lock, then try the second.

deadlock.c
#include <pthread.h>
#include <stdio.h>
#include <time.h>

static pthread_mutex_t m1 = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t m2 = PTHREAD_MUTEX_INITIALIZER;

static void pause_a_moment(void)          /* widen the window so it always happens */
{
    struct timespec t = { 0, 100000000L };    /* 100 ms */

    nanosleep(&t, NULL);
}

static void *thread_a(void *arg)
{
    (void)arg;
    pthread_mutex_lock(&m1);
    pause_a_moment();
    pthread_mutex_lock(&m2);              /* waits for B, who waits for A */
    puts("A got both locks");
    pthread_mutex_unlock(&m2);
    pthread_mutex_unlock(&m1);
    return NULL;
}

static void *thread_b(void *arg)
{
    (void)arg;
    pthread_mutex_lock(&m2);              /* opposite order: the bug */
    pause_a_moment();
    pthread_mutex_lock(&m1);
    puts("B got both locks");
    pthread_mutex_unlock(&m1);
    pthread_mutex_unlock(&m2);
    return NULL;
}

int main(void)
{
    pthread_t a, b;

    pthread_create(&a, NULL, thread_a, NULL);
    pthread_create(&b, NULL, thread_b, NULL);
    pthread_join(a, NULL);                /* never returns */
    pthread_join(b, NULL);
    return 0;
}

The 100 ms pause in the program only widens the window so that the problem appears on every run. Without it the program would usually work, and fail only occasionally, which is harder to find.

The usual fix: one lock order for everyone

If every thread takes m1 before m2, a circular wait cannot form, so the deadlock cannot happen. In deadlock_fixed.c, only thread_b changes:

Real runs (Linux sandbox) 
$ timeout 3 ./deadlock          (no output; killed by timeout after 3 s, exit status 124)
$ ./deadlock_fixed
A got both locks
B got both locks

In 50 of 51 runs A printed first; in one run B did. The fix guarantees that both threads finish, not which one goes first: whoever takes m1 first wins, and the scheduler decides that.

A second tool is pthread_mutex_trylock(), which returns an error instead of waiting when the mutex is held; a thread can then release what it holds and retry, which removes the hold-and-wait condition. OSTEP’s chapter on common concurrency problems discusses both techniques.

6. Condition variables: waiting for a change

A mutex answers “who may touch the data now”. It does not answer “wait until the data is in the right condition”. Polling in a loop wastes the core. A condition variable lets a thread sleep until another thread announces a change. OSTEP describes it as an explicit queue that threads put themselves on when some state of execution is not as desired.

The classic example is a producer and a consumer sharing a box that holds one item.

condvar.c
#include <pthread.h>
#include <stdio.h>

static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t can_put  = PTHREAD_COND_INITIALIZER;
static pthread_cond_t can_take = PTHREAD_COND_INITIALIZER;
static int full = 0;                      /* the predicate: is the box full? */
static int box = 0;                       /* holds at most one item */

static void *producer(void *arg)
{
    int i;

    (void)arg;
    for (i = 1; i <= 5; i++) {
        pthread_mutex_lock(&m);
        while (full)                      /* re-check after every wakeup */
            pthread_cond_wait(&can_put, &m);
        box = i;
        full = 1;
        printf("put  %d\n", i);
        pthread_cond_signal(&can_take);
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

static void *consumer(void *arg)
{
    int i;

    (void)arg;
    for (i = 1; i <= 5; i++) {
        pthread_mutex_lock(&m);
        while (!full)
            pthread_cond_wait(&can_take, &m);
        printf("took %d\n", box);
        full = 0;
        pthread_cond_signal(&can_put);
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

int main(void)
{
    pthread_t p, c;

    pthread_create(&c, NULL, consumer, NULL);
    pthread_create(&p, NULL, producer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}
  • pthread_cond_wait(&cv, &m) releases the mutex and blocks the thread as one atomic step. When the thread wakes, the call re-acquires the mutex before returning (POSIX.1-2024).
  • pthread_cond_signal() unblocks at least one thread waiting on the condition variable. If none is waiting, it has no effect: the signal is not remembered. That is why the state is kept in a variable (full) and not only in the signal.
  • Waits go in a while loop that re-checks the predicate. A wait may return when the predicate is still false: POSIX allows spurious wakeups, and another thread may also have taken the item between the signal and the wake.

7. Thread lifetime: why main waits

A thread ends when its start routine returns or when it calls pthread_exit(). A process ends when main returns (which behaves like calling exit()) or when any thread calls exit(); that ends all of its threads, finished or not. A pthread_join in main is what keeps the process alive until the worker is done. Drag the slider to move time forward and compare the two cases.

8. Thread-safe functions

A function is thread-safe if it can be called by several threads at once without breaking. POSIX requires almost all of its functions to be thread-safe and lists the exceptions (POSIX.1-2024, XSH 2.9.1). The list includes strtok, localtime, strerror and setenv. Several have a thread-safe replacement taking caller-provided storage: strtok_r, localtime_r, strerror_r.

strtok is the plain example. It remembers where it stopped in a hidden variable shared by every caller. Step through two threads splitting two different strings at the same time.

A single-threaded program such as a small shell can use strtok safely: only one caller ever touches the hidden variable. The problem begins when a second thread calls it. Some libraries make their own strtok safe in practice; POSIX does not require it, so portable code uses strtok_r.

9. Build and run on Cygwin

Cygwin provides the POSIX threads interface, and GCC’s -pthread option applies to it. The commands, from the folder holding the six .c files:

gcc -std=gnu90 -Wall -Wextra -pedantic -pthread hello_threads.c -o hello_threads
gcc -std=gnu90 -Wall -Wextra -pedantic -pthread race.c    -o race
gcc -std=gnu90 -Wall -Wextra -pedantic -pthread mutex.c   -o mutex
gcc -std=gnu90 -Wall -Wextra -pedantic -pthread deadlock.c       -o deadlock
gcc -std=gnu90 -Wall -Wextra -pedantic -pthread deadlock_fixed.c -o deadlock_fixed
gcc -std=gnu90 -Wall -Wextra -pedantic -pthread condvar.c -o condvar

./hello_threads
for i in 1 2 3 4 5; do ./race; done
for i in 1 2 3 4 5; do ./mutex; done
timeout 3 ./deadlock; echo "exit status $?"
./deadlock_fixed
./condvar
  • hello_threads: the order of the three lines may change from run to run; on some machines one order dominates, so run it many times (for i in $(seq 100); do ./hello_threads; done | sort | uniq -c counts the lines).
  • race: totals below 2000000 on some runs are the data race made visible. A build with -O2 may print the correct total every time; that proves nothing.
  • mutex: always 2000000, usually a bit slower than the unlocked version.
  • deadlock: prints nothing and never ends; timeout 3 stops it after three seconds with exit status 124 (Ctrl+C also works).
  • deadlock_fixed and condvar: finish normally, with the output shown in sections 5 and 6 (in deadlock_fixed, A and B may print in either order).
ThreadSanitizer is not expected to work on Cygwin. The Clang documentation lists its supported platforms as Android, Darwin, FreeBSD, Linux and NetBSD; Cygwin is not among them. The report in section 3 came from Linux. Data races on Cygwin are found by reasoning, as in the animations above, or by running the same source on a Linux machine.
